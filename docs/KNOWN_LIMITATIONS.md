# Known limitations

Short list of behaviours that are deliberate or accepted for now.

- **Trusted proxy ranges.** `api-core` trusts `X-Forwarded-For` from any peer in the private ranges (10/8, 172.16/12, 192.168/16) by default. A client that reaches `api-core` directly from such a network can choose its own address for per-client rate limits. Narrow `TRUSTED_PROXIES` to the proxy address when `api-core` is reachable from a private network other than the Compose one.
- **Shared client bucket behind NAT.** Per-client limits (auth, API key requests) are keyed by address, so clients behind one NAT or one proxy address share a bucket.
- **Redis outage.** Requests authenticated with an API key (ingestion) are answered with 503 while Redis is unavailable, because the rate limiter fails closed.
- **Isolation Forest false positives.** On clean seasonal data the min-max normalised score with the fixed 0.65 threshold flags roughly 7 percent of points. The z-score detector does not have this issue; the threshold is not tuned per metric. Accepted for now.
- **Model refit on restart.** Only the parameters of the Isolation Forest are stored, not the fitted model (accepted trade-off). After an `analytics` restart each model is refitted on the next run.
- **Ticket in the URL.** The stream ticket travels in the query string (30 s, single use). Any proxy or log in front of `api-core` must not record the query string; an access log that does would hold a short-lived credential.
- **HMAC without a timestamp.** `X-Internal-Signature` covers the body only, so a captured request can be replayed. This is harmless for `notify` because it is idempotent and publishes only database state.
- **Single scheduler.** The scoring scheduler runs inside the `analytics` process; run exactly one replica. The Redis lock only prevents overlapping runs, it is not a leader election; a second instance would only skip runs, not share the work.
- **One anomaly per point.** The detectors report each flagged point as its own anomaly with a window of that single point; adjacent anomalous points are not merged into one event.
- **Anomaly feed order.** `GET /api/v1/anomalies` is sorted by `window_start`, not by the time the anomaly was detected, so a late detection can appear among older entries.
- **Stream limits.** Each tenant may hold 10 live streams (`ANOMALY_STREAM_MAX_PER_TENANT`) and an instance 500; more are refused with 429. Streams end after 30 minutes or at token expiry and are not replayed.
- **End-to-end check is not part of push or pull request builds.** `.github/workflows/e2e.yml` runs `scripts/e2e/run.py` nightly and on manual dispatch only. A failure shows up the next day, not on the commit that caused it.
- **Acknowledgements and the expected range.** There is no SSE event for acknowledgements, so a second tab learns of an acknowledgement at its next re-sync; the API exposes no per-bucket mean or standard deviation, so the metric chart draws no expected-range band.
- **Alert delivery is at least once.** A crash after the receiver answered, or a lost response, repeats a webhook. Every request carries `X-Pulseboard-Event-Id` (and the event id in the body); receivers must deduplicate on it. Webhooks are signed with `ALERT_WEBHOOK_SIGNING_SECRET` (hex HMAC-SHA256 over `timestamp + "." + body`, headers `X-Pulseboard-Timestamp` and `X-Pulseboard-Signature`); without the secret the `WEBHOOK` channel is switched off and rules for it are refused.
- **Webhook targets are restricted.** Only `https` URLs with a DNS name (no IP literal, no credentials, port 443 unless `ALERT_WEBHOOK_ALLOWED_PORTS` says otherwise) whose every address is public are accepted, when a rule is saved and again for each delivery. The connection goes to the address that was checked, redirects are never followed and the response body is never read. A receiver on a private network or a Compose service name cannot be reached on purpose. `ALERT_WEBHOOK_ALLOW_HTTP` and `ALERT_WEBHOOK_ALLOW_PRIVATE_TARGETS` exist for tests and local development only; the application refuses to start with them outside the `test` and `local` profiles.
- **Alerts fail closed on a Redis outage.** The cooldown and the per-tenant event budget live in Redis. While it is unreachable, ingestion and anomaly notifications still succeed but no alert event is created, and the points or anomalies of that time are not evaluated again later.
- **Threshold evaluation is per batch.** A rule fires at most once per ingestion batch, reporting the latest crossing point; points older than one hour (`ALERT_MAX_POINT_AGE`) or more than five minutes ahead never fire it, so back-filled history raises nothing. At most 20 rules per metric and 200 per batch are evaluated. Enabled rules are cached for 5 seconds, so a change made on another instance takes up to that long to apply.
- **Alert events are budgeted.** A tenant creates at most 600 events per hour (`ALERT_EVENTS_PER_PERIOD`); the excess is dropped, counted (`pulseboard.alerts.events.suppressed`) and logged once per hour and tenant. Deleting a rule deletes its events.
- **The per-receiver circuit breaker is per instance.** After 5 consecutive failures to one host and port its deliveries are postponed for 60 seconds on that instance; other instances keep their own count. `EMAIL_LOG` only writes a log line, there is no SMTP.
- **One signing secret.** All webhooks of all tenants are signed with the single `ALERT_WEBHOOK_SIGNING_SECRET`; there is no per-rule or per-tenant secret and no rotation with an overlap period.
- **Rule cache and circuit breaker are in memory.** Both live per `api-core` instance and are lost on restart (see the entries above for the effect).
- **Alert events are never cleaned up.** There is no retention job; `alert_event` rows stay until their rule is deleted.
- **Evaluation after commit can be lost.** Threshold and anomaly rules are evaluated after the data is committed. If the instance crashes between the commit and the creation of the event, that alert is never raised. Only the delivery is an outbox.
- **No live alert events and no test event.** The dashboard learns of new alert events through its refresh (history page polls every 30 s while an event is pending); there is no SSE event, and there is no endpoint that sends a test event to a webhook.
